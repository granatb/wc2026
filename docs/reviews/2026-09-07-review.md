**evmax review — 7 September 2026**

Reviewed checkout: `main`, commit `8a225b5`. Review covers the shared simulation, FPL priors/scoring/selection, forecast publishing, grading and benchmarks, World Cup backtesting, browser/MCP surfaces, dependency security, and strategy/results. Production code and historical records were not changed.

**Assessment**

The project has a useful product concept and substantial working infrastructure. Its strongest asset is the possibility of a public, reproducible decision record. The implementation does not yet support the strength of its accuracy, immutability, and joint-simulation claims. Several defects directly affect points and rankings; others allow historical results to change when old gameweeks are rebuilt or graded again.

The next investment should be scoring correctness and a trustworthy evaluation pipeline, followed by minutes modelling. More pages, model complexity, or simulation runs will not resolve those problems. There is currently no demonstrated predictive or decision-making advantage over credible alternatives.

Priorities below mean: **P1** fix before relying on the affected results or claims; **P2** address in the next reliability/model iteration. They are review priorities, not CVSS security ratings.

**Confirmed findings: model correctness**

**1. P1 — Midfielders never receive clean-sheet points.**

[core/engine_events.py:303](/Users/bartlomiej.granat/personal/projects/wc2026/core/engine_events.py:303) only increments clean sheets for DEF/GK. The hook at line 325 repeats that restriction, so FPL's per-simulation scorer never receives a true clean-sheet flag for a midfielder even though `CS_PTS['MID']` is 1. The shared defect also affects FIFA's midfielder clean-sheet term.

A synthetic midfielder with 100% appearance probability against an opponent with zero goal intensity received **0 clean sheets in 5,000 simulations**, despite reaching 60 minutes in 99.54% of them. The official Premier League explanation confirms the [one-point midfielder clean-sheet award](https://www.premierleague.com/en/news/4361991/). Fix event eligibility independently from the defender/goalkeeper conceded-points rule and test the complete engine-to-points path.

**2. P1 — BPS adds historical scoring events a second time.**

[games/fpl/model.py:645](/Users/bartlomiej.granat/personal/projects/wc2026/games/fpl/model.py:645) uses total realized BPS per 90 as the baseline. [bps_from_row:152](/Users/bartlomiej.granat/personal/projects/wc2026/games/fpl/model.py:152) then adds appearance, goal, assist, save, clean-sheet and discipline BPS without subtracting their historical contribution. These are additions, not the “deltas” described in the comment. Historical goals and clean sheets consequently remain part of the baseline on top of newly simulated events. Early-season total BPS also carries very little evidence.

Estimate residual BPS after removing explicitly modelled components, with shrinkage and uncertainty, or use a simpler calibrated bonus predictor. Test bonus rank against held-out matches. Penalty/open-play differentiation is separately acknowledged as missing; the [official BPS changes](https://www.premierleague.com/en/news/4679946/whats-new-in-202627-fantasy-changes-to-bonus-points-system) reinforce the need to version the scoring implementation.

**3. P1 — Goal/assist allocation permits impossible outcomes.**

[core/engine_events.py:283](/Users/bartlomiej.granat/personal/projects/wc2026/core/engine_events.py:283) distributes the full team goal count twice, independently, once to scorers and once to assisters. It never excludes the scorer, despite the module description saying otherwise. A synthetic sole scorer/assister received both in 4,354 of 5,000 simulations. With one eligible player, every such assist is necessarily a self-assist.

The implementation also lacks an explicit unassisted-goal probability; its “unmodelled teammate” sink is not a calibrated substitute. Allocate each goal once, then an eligible assister or an unassisted outcome. This affects means, bonus and the distribution tails used to recommend captains.

**4. P1 — Minutes do not control attacking exposure, and starting is treated as appearing.**

[core/engine_events.py:282](/Users/bartlomiej.granat/personal/projects/wc2026/core/engine_events.py:282) draws players independently from start probabilities, assigns whole-match goals/assists, and only then draws minutes. A nonstarter cannot make a substitute appearance. Changing expected minutes alone does not reduce goal/assist exposure. Multiple goalkeepers and unrealistic numbers of teammates can play simultaneously, including in the bonus competition. Full-match conceded goals also apply after a player has been substituted.

At minimum, distinguish start/cameo/DNP and scale event exposure by minutes. Prefer a coherent team lineup and substitution model before presenting tails as realistic joint outcomes. The documented transfer-role problem in `core/fpl_priors.py:67` remains real: a 38-match historical role overwhelms a new club's role. It needs an expiring role prior, not only permanent manual notes.

**5. P2 — Dixon–Coles correction is fitted but discarded by the shared simulation.**

[core/espn.py:245](/Users/bartlomiej.granat/personal/projects/wc2026/core/espn.py:245) fits lambdas and rho. [core/engine_events.py:268](/Users/bartlomiej.granat/personal/projects/wc2026/core/engine_events.py:268) samples two independent Poisson counts; `Fixture` does not carry rho. Example from cached GW3 Fulham–Palace: fitted DC draw probability 27.81%, versus 25.41% under the distribution actually sampled. The Målspillet model separately uses the DC grid correctly.

Pass the corrected score grid into the fantasy simulation, or accurately describe the fantasy model as independent Poisson using DC-fitted rates. Test empirical score frequencies against the intended distribution, not only the fitting functions.

**6. P2 — Defensive contributions and goalkeeper saves are inconsistent with the claimed player priors.**

[core/fpl_priors.py:335](/Users/bartlomiej.granat/personal/projects/wc2026/core/fpl_priors.py:335) returns any nonzero current-season DefCon rate without shrinkage. Thus one noisy live sample bypasses the history/prior correction applied to backfilled data; a live zero switches back to history. Meanwhile [core/engine_events.py:310](/Users/bartlomiej.granat/personal/projects/wc2026/core/engine_events.py:310) ignores the populated `saves_per90`, drawing saves from `ga + 1.5` instead. Blend DefCon continuously by evidence and model saves from shot exposure/player ability. Evaluate threshold-event calibration, not just average counts.

**14. P2 — Stable identity and a single forecast vintage are not end-to-end invariants.**

The benchmark is sourced from a separate live horizon file rather than the exact final published forecast. Use `(season, element_id)` internally, explicit external mappings, and an artifact ID tying every evaluated column to its capture time and model version.

**Methodology and approach**

**MAE should not be the main proof of an expected-points model.** Expected points are means; squared error is aligned with estimating means, while absolute error rewards medians. Keep MAE for readability, add RMSE/MSE for xPts, proper distribution scores such as CRPS, and Brier scores for appearance/60-minute/haul events. See [Gneiting, Making and Evaluating Point Forecasts](https://arxiv.org/abs/0912.0902). Report calibration and uncertainty by gameweek/match cluster. A large mass of DNP players can make all-player MAE small; the same GW3 model scores 1.263 overall and 2.460 at 60+ minutes. The universal “2.5 state of the art” and “2.8 noise ceiling” language has no defensible population-independent meaning and should be removed.

**The duel is an engaging case study, not a controlled model-versus-human experiment.** Consensus changes from expert mentions in GW1 to an ownership heuristic and wildcard in GW2, with manual exceptions. Ownership is not a direct measure of starting-XI preference or captain votes. The model itself incorporates human/LLM research overrides and discretionary transfer decisions. Preserve the narrative but label it “our managed model-assisted squad versus our defined consensus policy.” Freeze both policies, keep chip/transfer budgets and overrides visible, and run shadow policies to isolate the value of research, forecasting and selection.

**The transfer score is not squad utility.** [games/fpl/transfers.py:100](/Users/bartlomiej.granat/personal/projects/wc2026/games/fpl/transfers.py:100) sums the incoming player's horizon points minus the outgoing player's. It does not reselect each week's XI, price expected autosubs/captain fallback, or value retaining a free transfer. A bench upgrade can receive the same delta as an XI upgrade despite very different expected team value. A -4 is priced for the single swap, but not a plan of linked moves. The current greedy squad builder is explicitly documented as a heuristic; the problem is treating its output as an exact optimum. First make the utility represent the actual game, then consider an exact solver.

**Do not diagnose every miss as variance after the fact.** Captaincy by highest reliable expected points is defensible, and one blank is not a reason to abandon it. But the projection supplying that decision has identified structural defects. The learning log repeatedly calls fixes “closed” when a gate/note was added, even though the same underlying role-estimation issue recurs. Track hypothesis, intervention and subsequent measured outcomes separately; reserve “validated” for independent evidence. Record the decision and alternatives before results arrive.

**Keep the product focus, reduce the claim strength.** Open data, accessible pages, a weekly decision record and readable explanations are worthwhile. They are not an established competitive moat or evidence of an edge. The only committed growth snapshot inspected, `evmax/assets/growth/gw1.json`, contains an empty `data` object. It cannot substantiate traction, retention, citations or conversion. Set up a modest measurable audience funnel before treating content volume as progress. The live accuracy page fetched during this review still showed two graded weeks; this is a freshness observation about the retrieved page, not a deployment audit.

**Code and operational reliability**

The separation between fetching, maths, scoring and rendering is useful. Deterministic seeds, a cache fingerprint, explicit missing-data handling in many boundaries, append-only learning notes, JSON exports and offline fixtures are good foundations. The complete Python suite passed **1,279 tests in 141.713 seconds**. ResourceWarnings identify some unclosed file handles but did not fail the suite.

The suite nevertheless misses the full-pipeline clean-sheet rule and permits the inconsistent benchmark semantics. Prioritize invariant/scenario tests: same-goal scorer cannot assist himself; no two starting keepers for one club; short minutes reduce attacking exposure; scoreline frequencies match the intended model; historical regrades are invariant to current state; common benchmark populations have identical IDs; late-only evidence is rejected. Independent scoring fixtures are more valuable here than more tests that repeat the implementation's formulas.

**Security**

The static public site has a relatively small attack surface: no inspected public write endpoint or database, browser team entry is processed locally, and the MCP implementation uses stdio and fetches public data. I found no obvious committed private-key, Anthropic-key, GitHub-token or AWS-access-key pattern in the current tracked text files. `.env` and `.wrangler` are ignored. This was a scoped pattern scan of the current tree, not a historical secret audit or proof that no credentials exist.

**P2: one vulnerable locked dependency.** `npm audit --package-lock-only --ignore-scripts --json` reports **one moderate vulnerable package, zero high/critical**: `qs` 6.15.3, at [mcp/package-lock.json:879](/Users/bartlomiej.granat/personal/projects/wc2026/mcp/package-lock.json:879), with two advisories: [array-limit bypass](https://github.com/advisories/GHSA-x5fp-wj9c-mxmx) and [attacker-controlled isBuffer denial of service](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g). The audit reports a fix available; 6.16.0 is outside the reported affected ranges. Update the lock and validate the MCP tools. The inspected server does not expose an HTTP query-parser endpoint, so the dependency finding is not evidence that the public site is remotely exploitable through these bugs.

No penetration testing, authenticated Cloudflare review, historical secret scan, installed Python vulnerability audit, or full MCP integration run was performed. This is a source/dependency review with local reproductions and read-only public-page checks. Legal conclusions in the strategy were not revalidated and should not be treated as part of this security assessment.

**Recommended sequence**

1. Before the next forecast: fix MID clean sheets, BPS residuals and scorer/assister consistency; introduce targeted full-pipeline rule checks. Publish a model-version change note. Preserve old forecasts as the old model's record.
2. Make the record trustworthy: freeze the full board plus ordered squad state and provenance, grade from stable IDs, enforce deadlines/finality, fix common-sample benchmarks, and disclose Round 3 and the GW3 late commit.
3. Establish evaluation: one predeclared forecast vintage, paired RMSE/MAE, event calibration and proper distribution scores; add fixed naive and external baselines. Keep descriptive results separate from evidence of statistical advantage.
4. Improve minutes/role and team-level decision utility. Shadow-run changes prospectively; estimate whether they help before switching the public decision policy. More simulations do not reduce uncertainty in assumed minutes or rates.
5. Complete the dependency/deployment hardening and reproducible archive build. Continue the weekly public record, but defer further feature expansion until the measurements can demonstrate progress.

The work so far proves the ability to ship and operate a transparent fantasy product. It does not yet prove a forecasting edge. Correctness and a reproducible record are the shortest route from the first achievement to the second.
